# SQR-247 External Retrieval Engineering Review

Generated by `/plan-eng-review` on 2026-05-27.

## Decision

Run a dev-only bakeoff using the existing LangSmith-backed eval datasets, pick a
winner, delete the temporary experiment harness, and ship only the winning
retrieval stack.

The shipped PR must not preserve generic provider switching, experiment
variants, local fallback, or unused provider data. It should contain the winner's
schema, indexer, runtime retrieval path, readiness checks, docs, and final eval
evidence.

## Accepted Scope

- Build temporary experiment support in an isolated path.
- Run every candidate variant against the full existing eval dataset.
- Choose the winner from a written decision rule before implementing the final
  production path.
- Prune all temporary experiment code and unused provider support before the
  final PR.
- Ship the winning stack only.
- If the winner changes vector dimensions, include the production reindex path
  and verify it during landing.

## Candidate Variants

Run these variants:

- current local Xenova embeddings with no rerank
- Voyage embeddings with no rerank
- Voyage embeddings with Voyage rerank
- Voyage embeddings with Cohere rerank, when `COHERE_API_KEY` is available

Do not include local embeddings plus external rerank unless the first bakeoff is
inconclusive. The goal is to choose the external retrieval stack to ship, not to
make local embeddings a long-term production candidate.

## Experiment Decision Rule

Correctness wins. The selected stack is the variant with the best full-dataset
pass rate and strongest retrieval evidence.

Latency and cost can veto only if they are clearly unacceptable for normal rule
searches. The experiment report must include:

- per-variant pass rate
- exact failing cases by variant
- retrieval evidence: top cited source/ref, source authority, and failure class
- latency and cost summary, including p50 and p95 when available
- candidate count used for rerank
- LangSmith experiment URLs
- selected winner and why it beat the alternatives

The experiment must not be judged only from the known flaky Poison cases.

## Architecture

During the temporary experiment, support local and Voyage embeddings honestly.
Do not pad local 384-dimensional vectors into a 1024-dimensional Voyage index.

The experiment storage model should use canonical rule-source chunks plus
dimension-specific embedding storage:

```text
rule_source_chunks
  id
  game
  source
  chunk_index
  text
  content_hash

rule_source_embeddings_<provider>_<dimension>
  chunk_id
  embedding_version
  embedding vector(<dimension>)
```

The final shipped schema should store only the winning embedding family. If
Voyage wins, production should not keep the local embedding table in the runtime
path.

Reranking belongs above pgvector search in a rule-source retrieval pipeline:

```text
searchRules/searchKnowledge
  -> rule-source retrieval pipeline
       -> embed query
       -> pgvector candidate search
       -> optional rerank
       -> deterministic source authority and condition-definition ordering
  -> citations/results
```

`vector-store` should stay focused on pgvector SQL. `tools.ts` should not grow
provider-client logic.

## Final Runtime Shape

After the experiment is pruned, the final runtime should hard-code the winning
provider stack in code and docs. Environment variables are allowed for the
winner's credentials and model tuning, but not for switching among unused
providers.

There is no local fallback or rollback path in the shipped PR. If credentials or
provider probes fail, readiness must fail closed with explicit errors.

## Test Plan

Experiment phase:

- Build and index all candidate variants in development.
- Run the full existing LangSmith eval dataset for each variant.
- Produce a written report with the decision rule above.

Final implementation phase:

- Add unit tests for the winning provider client and error handling.
- Add integration tests for final schema/index/search behavior.
- Add tests that readiness fails clearly when required credentials or provider
  probes are unavailable.
- Run `npm run check`.
- Run a full LangSmith eval on the final pruned shipped stack.
- Compare final shipped-stack eval results with the experiment winner and
  document any drift.

## Performance Plan

- Use fixed rerank candidate caps before running the bakeoff. Start with top 40
  rule chunks into rerank unless the experiment shows that this cap blocks
  correctness.
- Report latency and cost per variant.
- If the selected provider changes vector dimensions, treat reindexing as part
  of landing, not a manual follow-up.
- Production verification must confirm the new vector index is populated and
  retrieval works after deploy.

## NOT In Scope

- Shipping generic provider switching.
- Shipping experiment variants as product/runtime behavior.
- Keeping local embeddings as a production fallback after an external stack
  wins.
- Moving away from Postgres + pgvector unless the experiment proves pgvector is
  the blocker.
- Adding a new eval dataset before the first bakeoff. The existing ground-truth
  datasets are the source of truth for this ticket.
- Solving LangSmith threads or incremental eval progress reporting.
