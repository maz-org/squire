## Step 0: Scope Challenge

### What already exists

- `src/chat/conversation-service.ts` already owns persisted chat turns,
  idempotency, retry behavior, failure persistence, and history selection.
- `src/server.ts` already owns browser-visible SSE translation, including
  terminal `done` and `error` events.
- `docs/ARCHITECTURE.md` already states the high-level persistence contract:
  user turn first, then assistant answer or persisted generic failure, with
  error turns excluded from future history.
- `docs/SSE_CONTRACT.md` already states stream event ordering and terminal
  success/error behavior.
- `test/conversation.test.ts` already covers:
  - non-SSE retry after `ECONNRESET`
  - no retry on SSE transport failure
  - duplicate assistant prevention for repeated same-key recovery
  - already-persisted assistant response reuse
  - bootstrap failure without an assistant row

### Minimum change

The smallest complete SQR-86 change is:

1. Add a short ADR for Phase 1 web chat reliability policy.
2. Update `docs/ARCHITECTURE.md` or `docs/SSE_CONTRACT.md` only where the
   permanent docs need current-state pointers.
3. Add focused tests for retry classifier boundaries:
   - exact transient transport errors get one retry on non-SSE
   - streamed/SSE turns never retry after an `ask()` call starts
   - provider/server-side errors are not retried
   - exhausted retry persists one generic failure turn and no duplicate answer

## Architecture Review

1. [P2] (confidence: 9/10) `src/chat/conversation-service.ts:20` and
   `docs/ARCHITECTURE.md:393` — The runtime behavior exists, but the durable
   policy does not name the retry budget, the exact retryable error classes, or
   the SSE no-retry rule.

   Recommendation: write an ADR, then point architecture/SSE docs at it. This
   matches the repo's rule that non-obvious decisions belong in ADRs rather than
   only comments or PR text.

2. [P2] (confidence: 8/10) `src/server.ts:882` — SSE failures always emit
   `kind: "transport"` for persisted `ask()` failures, even when the underlying
   cause was a provider/server-side error.

   Recommendation: do not broaden SQR-86 into error taxonomy refactoring.
   Document Phase 1's browser behavior as "recoverable generic chat failure"
   and defer richer operator-visible error classification to SQR-87.

## NOT in Scope

- New retry middleware, queueing, or background jobs. The Phase 1 web path is
  synchronous and already has one narrow retry point.
- Retrying streamed/SSE turns after `ask()` starts. The browser may have already
  received partial answer text, so replaying silently would mix two attempts.
- Operator metrics implementation. SQR-87 owns observability and trace
  correlation; SQR-86 should name the signals, not build the metrics stack.
- Cost budgets or model-call accounting. SQR-60 owns cost controls.
- Provider SDK migration. ADR 0013 keeps Phase 1 production on the current
  service and conversation boundaries.
